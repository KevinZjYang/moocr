## 1. PDF 逐页

### 为什么在渲染进程渲染

pdf.js 需要 canvas，主进程没有 DOM。所以 PDF 的拆页发生在渲染进程：

```
主进程 read-pdf → Uint8Array
        ↓ (IPC)
渲染进程 renderPdf() → 每页一张 JPEG dataURL
        ↓ (identify targets)
主进程 → runPage({ imageUri }) → llama-server
```

主进程只碰字节，不碰像素。这也让「PDF 页」和「图片」在 IPC 上统一成同一种东西（`IdentifyTarget`），后面的管线只有一条。

### 参数选择

`apps/renderer/src/pdf.ts`：

```ts
renderPdf(data, { maxEdge = 1600, quality = 0.9, maxPages = 200 })
```

- `maxEdge = 1600`：直接决定 prefill 成本。M0 测得 image token ≈ **950 token/MP**，1 MP 左右一页约 950 token、预填 ~0.6 s；1600 长边对 A4（1.4:1）约 1.3 MP，落在 `standard` 预设的 2560 预算内。调大会撞上 M0 记录的超线性墙（2.35 MP 预填 2.3 s，9.4 MP 预填 27.7 s）。
- `quality = 0.9`：JPEG 压缩痕迹会影响细小汉字，0.9 是能看出差别之前的最后一档。
- `scale = min(3, maxEdge / max(w, h))`：上限 3 是为了不把 200 DPI 的扫描件放大成假的清晰度——放大不会增加信息。
- 先 `fillStyle = '#fff'` 铺白底：PDF 的透明背景转 JPEG 会变黑，模型会把整页当深色底处理。

### 实测

`fixtures/synth/sample-3p.pdf`（3 页：混排段落 / 合并单元格表格 / 公式）：

```
p1 mix-en-zh      1070 in / 95 out / 1.22 s / prefill 1788 tok/s / decode 164 tok/s
p2 table-merged   219 字
p3 formula-simple 254 字
```

三页串行约 4 s（含首次预热外的稳定态）。UI 侧栏显示 `sample-3p.pdf · p1/p2/p3`，点任意一页看该页结果。

## 2. 导出

`packages/exporters`，三种格式共用 `ExportPage[] = { label, markdown }[]`。

### Markdown

单页直接输出内容（不加标题，方便粘进笔记）；多页每页一个 `## label`，用 `\n\n---\n\n` 分隔。

### HTML

`packages/postprocess/html.ts` 的 `toHtml()` 生成自包含文档（内联 CSS、无外链）。关键约束：

- 表格是我们自己从 OTSL 生成的 `<table>`，**整块原样保留**，不做 escapes；其余文本才 escape。
- `parseTableHtml()` 把 HTML 表格还原成 `HtmlCell { text, colspan, rowspan, header }`，供 DOCX 复用同一份结构——不让两种格式各写一遍合并单元格逻辑。
- CSS 带 `prefers-color-scheme: dark`，导出的文件在深色系统下也读得下去。

### DOCX

`packages/exporters/src/docx.ts`，用 `docx@9.15.2` 的 `Packer`。

- `tableFromHtml()` → `TableCell` 的 `columnSpan` / `rowSpan`（**只在 >1 时才设**，否则 Word 会把每个格子都写成 span=1 导致表格塌陷）。
- 表头 `shading: { fill: 'F2F4F7' }`。
- 正文字体 `Microsoft YaHei`、size 22（11 pt）。
- LaTeX → **OMML**（Word 原生公式），详见下面「公式导出」。

### 公式导出：LaTeX → OMML

第一版把 LaTeX 写成等宽纯文本，理由是「Word 不认 LaTeX，给原文最诚实」。实际用起来是错的：用户看到的是
`E = m c ^{2}\] \[ \int_ {- 0 ^ {\infty}} …` 这种源码，公式页等于没导。

现在走 `temml`（LaTeX → MathML）→ `mathml2omml`（MathML → OMML）→ `ImportedXmlComponent.fromXmlString()`：

```
LaTeX ──temml──> MathML ──mathml2omml──> <m:oMath/> ──docx──> Word 原生公式
```

要点：

- **两个库的 ESM 出口都反直觉**。temml 的 API 挂在 `default` 上（直接调 `temml.renderToString` 会 `is not a function`）；mathml2omml 导出的是命名函数 `mml2omml`（默认导出 `default` 不存在）。都在 `math-omml.ts` 里统一处理。
- **`\begin{array}{l} … \end{array}` 要拆行**。模型把整页公式压成一个 array 环境、用 `\\` 分行；原样丢给 Word 会变成一个竖排矩阵。`splitArrayRows()` 按 `\\` 拆成独立公式，逐条居中成段，还要顺手去掉 `[2pt]` 这类行距参数。
- **单条公式转换失败不能炸整份文档**。`latexToOmml()` 任何一步失败返回 `null`，该行回退等宽文本，其余公式照常渲染。
- 命名空间：`mathml2omml` 的输出通常已带 `xmlns:m`，缺失时由 `withMathNs()` 补在 `<m:oMath>` 上；最终 docx 库会把它提到根元素。

同一个改动还修了两个连带 bug：

1. **`splitBlocks` 吞内容**。旧实现从 `\[` 一路收集到「含 `\]` 的行」，但模型常写成单行 `\[…\]`，于是它把后面所有段落一起吃进公式块，导致公式转换失败、整段回退纯文本。改为：先判断首行是否已闭合，闭合就只取首行。
2. **有序列表全变成 1.**。模型输出 `1. 引言` / 空行 / 正文 / `2. 方法`，被 `splitBlocks` 拆成多个独立 `ol` 块，每块从 1 计。现在跨块继承编号，遇到 `heading` 才归零（HTML 导出同步修，用 `<ol start>`）。

验证：`scripts/m5-export-e2e.mjs` 走完整链路（识别 3 张图 → 导出 docx），再用 Word COM 转 PDF 渲染核对——4 条块公式（积分、根号、求和、上下标）与 2 条行内公式都是 Word 原生公式，表格 `rowspan`/`colspan` 正确，列表编号 1/2/3 连续。截图见 `docs/m5-docx-p1.png`。

### 实测

27 页整批（`out/*.md` → `out/_export/all.*`）：

```
all.md    31,654 B
all.html  35,926 B   4 个 <table>、1 个 colspan、2 个 rowspan
all.docx  16,644 B   zip 头 504b
```

真实链路（识别 3 张图后直接导出，`out/_m3/real/`）：

```
real.md     887 B
real.html 2,883 B   1 表，colspan 保留
real.docx 10,603 B  504b
```

公式页单独验证（`out/moocr-e2e.docx`，10,813 B）：`word/document.xml` 里 6 个 `<m:oMath>`、0 处 LaTeX 源码残留。

### 一个坑：preload 只收一个参数

第一版验证脚本写的是 `window.moocr.export(req, savePath)`，而 preload 里是 `export: (req) => ipcRenderer.invoke('export', req)`——第二个参数被静默丢弃，主进程拿不到 `savePath`，于是弹出保存对话框，无头环境下**直接卡死**（跑了 5 分钟没输出）。

现在 `savePath` 放进了请求体：

```ts
window.moocr.export({ format, pages, defaultName: 'real', savePath })
```

`savePath` 存在时跳过 dialog，仅供自动化测试；正常 UI 路径永远走 `dialog.showSaveDialog`（代码里有注释标明这是测试后门）。

## 3. KIE

### schema 用「示例对象」，不用 JSON Schema 元语言

这是 M3 最大的一处返工。

第一版 `KIE_SCHEMA` 写成标准的 JSON Schema：

```json
{ "type": "object", "properties": { "store_name": {...}, "items": {...} }, "required": [...] }
```

结果模型**完全不认**：它忽略了所有 `properties` 键，自己编了一套字段（`地区描述`、`customer_id`、`item_name`、`item_price`、`tax_time`…），还把结果包成了数组 `[{...}]`。

改回 M0 实测过的那版措辞——扁平模板 + 明确指令：

```
Extract key information in the image

Please output the key information in JSON format according to the following schema:
{
  "date": "",
  "seller_address": "",
  "seller_gst_id": "",
  "seller_name": "",
  "total_amount": "",
  "total_tax": ""
}
```

同一张收据立刻变成 6 个键全对，和 M0 的记录一致：

```json
{
  "date": "2017-10-18",
  "seller_address": "LOT 1851-A & 1851-B, JALAN KPB 6, KAWASAN PERINDUSTRIAN BALAKONG, 43300 SERI KEMBANGAN, SELANGOR",
  "seller_gst_id": "001092886528",
  "seller_name": "MR. D.I.Y. SDN BHD",
  "total_amount": "5.90",
  "total_tax": "0.33"
}
```

结论写进 `packages/core/src/prompts.ts` 的注释里：**这个模型读的是「照这个样子填」的示例，不是 schema 语义**。所以 `KIE_SCHEMA` 的默认值就是字段名 + 空字符串。

为了不把这条路堵死，`toTemplate()` 仍然接受用户粘贴完整 JSON Schema——检测到 `properties` 就取出键名重新拼成扁平模板。UI 的「字段 schema」面板允许直接改这份 JSON。

### 容错

模型即使被要求「输出一个 JSON 对象」，仍然时不时包一层数组。`pipeline.ts` 里：

```ts
if (Array.isArray(json) && json.length === 1 && typeof json[0] === 'object') json = json[0];
```

多元素数组保留原样（那通常意味着它真的识别到了多张单据）。

解析失败时降级为纯文本 + 告警 `KIE 输出不是合法 JSON，已按原文返回`，不吞掉内容。

### 退化重试不走 document prompt

其他任务退化时，守卫会换 `PROMPTS.document` 重试一次——因为 document 是最强的兜底。**KIE 不能这么做**：换成 document 会丢掉 JSON 结构，重试等于白跑。所以 kie 用同一个 prompt 再试一次，仍退化的才截断。

测试里锁死了这条：`KIE 重试仍用 kie prompt`。

### 一个坑：`file` 是标签，不再是路径

M3 把 `IdentifyTarget` 从「路径」改成「标签 + 路径或位图」，因为 PDF 页没有独立路径。但 `runPage()` 在没有 `imageUri` 时会拿 `req.file` 当文件路径去读——于是报：

```
ENOENT: no such file or directory, open 'E:\Github\moocr\receipt'
```

修法在主进程：**统一在 IPC 边界把路径转成 dataURL**，`file` 从此只当显示用。

```ts
const uri = t.imageUri ?? (t.path ? await imageDataUri(t.path) : undefined);
```

顺带的好处：`runPage` 不再依赖 cwd，测试里传假的 `file` 也不会去碰磁盘。

## 5. 已知限制

- **热键截图没做**。M4 的第一件事。
- **PDF 逐页串行**。3 页 4 s 尚可，200 页要 4 分钟。`runBatch` 的并发池已经在 core 里，UI 层没接——因为并发时显存会抖，M4 要和 region 加速一起调。
- **PDF 的分页边界不看内容**。跨页的表格会被拆成两个表，跨页的段落会被切成两段。这需要版面分析才能修，和 region 模式是同一个前置条件。
- **DOCX 的公式是等宽文本**，不是 Word 公式对象。
- **没有反向校验**：导出之后不会重新解析 DOCX 检查结构是否完整，只有字节数和 zip 头的粗检。
