# M1 —— 识别管线与 CLI

M1 的目标是**把模型能力包成可复用的管线**，并在没有 UI 的情况下端到端跑通。
产物：`packages/{inference,postprocess,core,cli}`，无构建步骤（Node 24 直接执行 `.ts`）。

---

## 1. 分层

```
packages/inference   llama-server sidecar 生命周期 + /v1/chat/completions 封装
packages/postprocess 纯函数：OTSL→HTML、Markdown 归一、退化检测      ← 无 IO，可单测
packages/core        单页/批量管线：prompt 选择、退化守卫、timings 聚合
packages/cli         参数解析、并发调度、落盘
```

依赖方向单向：`cli → core → {inference, postprocess}`。`postprocess` 不依赖任何 IO，
所以 M2 的渲染进程可以直接复用同一份代码（通过 IPC 或打包）。

**为什么不用 Webpack/Vite 构建 core**：Node 24 原生支持执行 `.ts`（type stripping），
引入构建步骤只会让 CLI 与 Electron 主进程的调试路径分叉。限制是不能用 `enum`、
`namespace` 和构造器参数属性 —— 代码里全部避开。

## 2. 数据流

```
图片 ──base64──┐
               ├─> POST /v1/chat/completions ─> 文本
任务 prompt ───┘                                │
                                                ├─> 退化检测（多尺度连续重复）
                                                │       └─ 命中? → 截断 / 换 prompt 重试
                                                └─> 渲染
                                                       ├─ table 任务：OTS​L → HTML <table>
                                                       ├─ document：内嵌 OTSL → HTML，其余原样
                                                       └─ text/formula：仅剥围栏
```

`PageResult` 是 M2 的接口契约（`packages/core/src/pipeline.ts`）：

```ts
{
  file, task, markdown, summary,
  timings: { wallMs, promptTokens, predictedTokens, prefillTps, decodeTps },
  attempts: [{ task, finishReason, chars, degenerated, wallMs }],
  finishReason, degenerated, warnings, raw
}
```

UI 需要展示的"耗时/为什么慢/是否重试过"全部在这里，不需要再去解析日志。

## 3. CLI

```bash
node packages/cli/src/main.ts <文件或目录...> [选项]

  --task <document|text|table|formula>  默认 document
  --preset <fast|standard|accurate|extreme>
  --max-tokens <n>                      默认按任务（document 4096）
  --out <目录|->                        默认 ./out；- 表示打到标准输出
  --json                                同时输出结构化元数据
  --attach <url>                        复用已在运行的服务
  --parallel <n>                        并发页数 = 服务槽数
  --port <n>                            默认 8090
```

预设与图像 token 预算（依据 `docs/CAPABILITY.md` §1.2 的 prefill 曲线）：

| preset | image-max-tokens | 适用 |
| --- | --- | --- |
| fast | 1024 | 印刷体轻页，0.3–0.6 s/页 |
| **standard** | **2560** | 默认。印刷文档精度已饱和 |
| accurate | 6144 | 手写、书法、小字密排 |
| extreme | 12288 | 极密排/超长表格，prefill 20 s+ |

每槽上下文自动算：`max(12288, imageMaxTokens + maxTokens + 512)`。单页最坏实测
10745 token（手写页 8230 图 + 2515 输出），所以 12288 是硬下限。

## 4. 退化守卫的策略来源

`docs/capability.json` 的实测结论决定了这条看似保守的逻辑：

- `document` prompt 在 12 组退化样本上**零退化**，真实页、nonce 生僻字页都是 0%。
- 只有 `text` prompt 在生僻字页崩过：输出 13.7% 准确率，尾部 `㕥` 连续重复 81 次。

所以：

1. `document` 任务退化 → 不重试（重试也还是同一个 prompt），只截断 + 告警。
2. `text`/`table`/`formula` 退化 → 改用 `document` prompt 重试一次（它更稳）。
3. 仍退化 → 截断尾部重复，标 `degenerated: true`，界面要显式提示"结果可能不完整"。

`finish_reason: length` 单独告警，不和退化混在一起 —— 两者的处置完全不同。

## 5. 一个被砍掉的设计

第一版实现过 `--keep-server`（跑完不杀 sidecar）与跨进程配置复用，用
`<log>.meta.json` 记录启动参数，复用前比对。**已删除**，原因：

- Windows 上 CLI 进程退出后 sidecar 会存活，下次运行读到陈旧 meta；
- 若端口被占用导致新进程绑定失败，而旧服务仍应答 `/health`，`waitForHealth`
  会立刻通过 → 拿到一个参数（image token 预算）与本次不一致的服务，**静默降精度**。
- 实测中这个组合真的发生过一次（`--preset accurate` 实际跑的是 2560 预算）。

现在：`startServer` 默认 `refuseIfBusy`，端口被占就报错并提示用 `--attach`；
`--attach` 时完全不碰 sidecar。生命周期的所有权永远唯一。

## 8. 已知限制（管线层面无法解决）

1. **韩语**：`주출`(추출)、`매리类`、`마克다은`、`정화도` 等，即使 44 px 大字、
   1099 image token 也一样错。字符级 86% 但语义已崩 —— 指标低估损伤。
2. **手写在 standard preset 下精度不足**：74%，要 85% 必须 `--preset accurate`
   （prefill 从 12 s 涨到 29 s）。CLI 无法自动判断手写，M2 需要让用户能一键切换重跑。
3. **无字符级坐标**：`probe-bbox` 直接要 bbox，模型只回 `[{"text": "..."}]`。
   只能做块级对照。
4. **表格偶发把值写成合并标记**：`table-merged` 出现过一次末列 `100` → `<ucel>`。
   OTSL 解析器对孤立的 `lcel/ucel` 会降级成空格 + warning，不会抛错。

## 9. M2 的接口约定

渲染进程不直接碰 HTTP，也不解析日志：

- 主进程持有一个 `RunningServer`（单例），渲染进程通过 IPC 请求识别；
- 请求体 = `{ filePath, task, preset }`，响应 = `PageResult`；
- 中途切换 preset → 需要重启 sidecar（约 8 s），UI 必须显示进度而不是卡住；
- 取消识别 = 对 HTTP 请求 `abort`，不要 kill sidecar。
