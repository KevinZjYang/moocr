# M4：可用性与分发

M4 的目标是「从能用变成顺手」：热键截图、并发、可靠性、打包。
全部结论都来自本机实测（Ryzen 5 5600X / Arc A770 16 GB / Q4_K_M / Vulkan）。

```
npm start          # 开发运行（构建 + 启动）
npm run pack       # 打免安装目录 release/win-unpacked
npm test           # 49 + 44 + 27 断言
npm run regress    # 与 M0 基线比准确率
```

---

## 1. 全局热键截图

`Ctrl+Shift+O`（`CommandOrControl+Shift+O`）→ 屏幕冻结 → 拖框 → 直接进识别队列。

实现分三块：

- `apps/desktop/src/capture.ts`：`desktopCapturer.getSources({types:['screen']})` 取每个显示器的缩略图，按 `source.display_id === String(display.id)` 配对；每屏开一个 `frame:false, transparent:true, alwaysOnTop:'screen-saver'` 的窗口铺满该屏。
- `apps/renderer/overlay.html` + `src/overlay.ts`：把截到的图当背景铺满，用 `box-shadow: 0 0 0 9999px rgba(8,10,14,.45)` 反向挖洞做遮罩，橙色边框 + 实时尺寸标签；Esc 取消，拖动不足 4px 也算取消。
- 落盘到 `%APPDATA%/moocr/captures/cap-<ts>.png`，主进程广播 `capture-done`，渲染进程加进列表并立刻识别。

三个细节值得记：

**裁剪比例不能用 `scaleFactor`。** `thumbnailSize` 会把截图缩放到给定尺寸（我们按最大屏虚拟分辨率给），此时 `image.getSize()` 与 `display.bounds` 的比例才是真实映射。早期用 `scaleFactor` 算，2 倍屏下框选区域整体偏移 2 倍面积。

**截之前要先藏窗口。** 自己的窗口会出现在截图里，且 `hide()` 到合成器真正移除有几十毫秒延迟 —— 实测 160 ms 是安全值，更短会偶尔截到残留的窗口阴影。

**DPI 非 100% 时坐标要按物理像素换算。** overlay 是 CSS 像素坐标，截图是物理像素，比例用 `image.getSize().width / bounds.width`。实测 4K@125% 下框选 400 DIP 得到 500×375 物理像素，尺寸标签显示的也是物理值（与用户在画图工具里看到的数字一致）。

## 2. 并发识别

`runBatch` 早在 core 里，M4 只是接线：并发数从 UI 传下来，`ensureServer` 三方比较（preset、parallel、实例）决定是否重启 sidecar，`-c` 上限随之变成 `ctxPerSlot × parallel`。

**实测结论：默认并发是 1，不是 2。**

| 场景 | 串行 | 并发 | 结果 |
|---|---|---|---|
| 8 张轻页（874 ms/页） | 6991 ms | p=2 7914 ms | **慢 13%** |
| 8 张轻页 | 6991 ms | p=4 6930 ms | 持平 |
| 3 张大页（dense-s100/150/200，7580 输入 token） | 36895 ms | p=3 23258 ms | **快 1.59×** |

原因：轻页的 874 ms 里固定开销（读图、base64、prompt 组装、HTTP、调度）占大头，GPU 计算只占小部分，多槽共享同一张计算图仍要排队，切上下文反而更贵。大页的收益来自 continuous batching —— 多序列共享同一份权重读取，decode 阶段是 memory-bound，这才是 1.59× 的来源。

所以 UI 上是 `1 — 默认 / 2 — 大页或长表格 / 4 — 大批量大页，约 8G 显存`，没有假装并发总是更快。显存按 M0 实测单槽 4.16 GB 外推，4 槽约 8 GB。

## 3. 可靠性：结果缓存 + 崩溃自愈

### 3.1 内容寻址的结果缓存

不引入「任务/队列」概念（要改 UI 数据模型，收益不明显），而是按
`sha256(图片字节) + 任务 + 预设 + 模型版本` 做内容寻址，命中直接返回。

模型版本用权重文件的 `size + mtime` 派生 —— 换了量化等级或新版权重，key 自然变化，不会误命中旧精度结果。

实测：

```
第 1 次 standard: 3339 ms · 310 字 · cached=false
第 2 次 standard:    3 ms · 310 字 · cached=true     ← 1113×
换 preset accurate: 3388 ms · 310 字 · cached=false   ← 正确失效
再回 standard:       2 ms · 310 字 · cached=true
```

这同时就是「断点续跑」：PDF 跑到第 7 页崩了，重启后前 6 页全部命中，只补跑剩下的。比维护一个 `.state.json` 状态机简单得多，也不需要处理「状态文件与结果不一致」。

命中时 `timings` 是首次识别的数字，报出来会误导，UI 只显示「缓存命中 + 字数」。菜单里有「清空识别缓存」。

缓存目录在 `%APPDATA%/moocr/result-cache`，不是仓库的 `resources/`。

### 3.2 sidecar 崩溃自愈

`runBatch` 增加可选 `runner` 参数，桌面端注入 `runPageResilient`：请求报 `ECONNREFUSED / ECONNRESET / EPIPE / socket hang up / fetch failed` 时，判定 sidecar 已死 → 重启 → 重跑该页（只重试一次）→ 发一条「推理服务中断，已重启并重试该页」。

实测：预热 → `taskkill /F /IM llama-server.exe` → 立刻再识别 → 成功，2.7 s 完成（含重启），`serverStatus.running === true`。

## 4. 打包

> 0.2.0 已把这一节的做法换掉：改为 NSIS 安装包 + 应用内下载权重，细节见 [M6 · 安装包与运行时下载](M6-RUNTIME.md)。下面保留 0.1.0 的原始记录，方便对照「为什么当时会缺运行时」。

0.1.0 用 `electron-builder` 的 `dir` target（免安装目录），再把目录压成 zip：

```
release/win-unpacked/            1.2 GB
  resources/app.asar              65 MB
  resources/resources/models     703 MB   ← Q4_K_M 529 MB + mmproj 207 MB
  resources/resources/llama/bin   45 MB
```

三个必须处理的点：

**`findRoot` 要认 `process.resourcesPath`。** 打包后资源在 `resourcesPath/resources/...`，开发时是向上找仓库根。两条路径都试，同一套代码。

**安装目录只读。** 装机版落在 `Program Files` 下，`.sidecar.json`、截图、缓存都不能写 `resources/`。三处都改到 `app.getPath('userData')`：
- 缓存 → `userData/result-cache`
- 截图 → `userData/captures`
- sidecar pid 记录 → `userData/state/.sidecar.json`（`startServer` 新增 `stateDir` 选项）

**`app.setName('moocr')` 要早于任何 `getPath`。** 否则 dev 模式 userData 落在 `.../Electron` 下，和装机版各写一份，pid 记录与缓存互不可见。

打包版实测：启动 → 命令行带 PDF 自动加载 3 页 → 识别 → 缓存命中 → 换 preset 重启 sidecar，全部正常。

## 5. region 加速：探测结论是「可以做，但不该现在做」

原计划 M4 第四项是版面检测 + 区域并发识别。探测结果：

- 有社区转的 ONNX：`alex-dinh/PP-DocLayoutV3-ONNX`；transformers 也在 2026-01 加了 `pp_doclayout_v3` 支持，说明官方权重可导出。
- 需要 `onnxruntime-node`（Windows 原生二进制）+ 切块 + 拼接 + 去重 + 「规整/不规整」判定 + UI 开关。

它没做的原因是**收益与风险不匹配**：

- 速度收益明确（9.4 MP 页 prefill 27.7 s → 切 8 块并发约 3–4 s），但只对超大页成立；A4 扫描件（1–2 MP，prefill 1–2 s）几乎无收益。
- 精度收益不确定。M0 实测印刷文档在 630 token 就有 97.0%，反而 2366 token 是 94.8% —— 说明该场景本来就不缺分辨率，切块换来的是速度不是精度。手写页确实靠分辨率（4000→8230 token 才 +10.4 分），但官方明确要求手写必须整页，切块会丢上下文。
- 风险高：切错边界直接丢内容，比慢更糟。

留到 M5，且必须满足：默认关闭、只对 `avg 像素面积 > 4 MP` 且「检测框规整」的图启用、整页模式一键可回。

## 6. 已知限制

- 热键注册只在 `whenReady` 试一次，被别的软件占用时只发一条 notice，不会重试或提示改键。
- 并发数只影响单次识别的并发；跨批次（多次点「识别」）仍然串行。
- 缓存没有容量上限，也不会按时间淘汰（`stats` 能看条目数与字节数，菜单可一键清空）。
- 安装包未签名，仍会触发 SmartScreen；只有 NSIS 安装版，没有 portable 单文件；无自动更新。
- 跨页表格仍然断成两个表：合并需要版面理解，与 region 是同一前置。

## 7. 复现

```bash
# 缓存正确性（首次冷跑 → 命中 → 换 preset 失效 → 回原 preset 命中）
node scripts/m4-cache-check.mjs 9222

# 崩溃自愈（强杀 llama-server 后继续识别）
node scripts/m4-recover-check.mjs 9222

# 并发对比（轻页 / 大页）
node scripts/m4-parallel-check.mjs 9222
node scripts/m4-parallel-big.mjs 9222

# 截图链路（overlay 配置、选区、落盘、自动识别）
node scripts/m4-capture-check.mjs 9222
```

前置：`node scripts/start-desktop.mjs --remote-debugging-port=9222`（或直接跑打包版 `moocr.exe --remote-debugging-port=9223`）。
